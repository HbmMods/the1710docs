# /What even is Forge

If you're reading this, you probably already know that Minecraft Forge is a mod loader, a piece of software that drills itself (metaphorically, of course) into the base game and alters it so it can load mods. Logically, said mods need to be written in a way to actually be compatible with Forge, so Forge offers a version that acts as a development kit (the "src" option on the Forge downloads, which got renamed to "mdk" in Minecraft versions 1.8 and up).

In broad terms, that's what Forge does. If we want to be *really* pedantic about it, then Forge as installed on a client is actually three different mods bundled together, that being the Minecraft Coder Pack (which is what offers deobfuscation), Minecraft Forge (the Forge API for mods to use) and the Forge Mod Loader (the thing that actually *loads* mods). However these distinctions are not really relevant for anything, nor something you have to care about when writing mods. Forget this paragraph exists.

## What Forge *does*
Well we know that Forge lets us run mods as well as develop them, but what does it do for us in the context of development?

* It allows us to load our mod. In more technical terms, it provides us with a way to register a class that is used to register all the actual working parts of a mod. Blocks, items and entities all need to be added to various registries for the game to recognize them, and by giving a class the `@Mod` annotation, we basically tell Forge "hey this is a mod's main registry class, please consider this when starting the game and doing all the initializing".
* As an extension of the previous point, it provides startup events. In a mod's main registry, methods with the `@EventHandler` annotation and the correct parameter type (that being a child class of `FMLEvent`) are turned into handlers that will run automatically during the mod's initializing phase (as well as a few other cases), depending on the exact parameter type used. There's multiple event types for different phases of startup (the differences we will get into later), as well as a few added events for when a server starts or stops or when handling missing mappings (i.e. when starting a world with missing registry entries, allowing us to handle those).
* It also provides a large number of gameplay events. The concept is similar to startup events, there needs to be a class that's registered as an event handler, and all methods in that class marked with the `@SubscribeEvent` annotation and a valid event class as the parameter will be considered as events, where the method is called whenever that event triggers. There's only a limited number of events in fixed places, so there's only so much they let you do, but events allow clean handling of certain things that would otherwise require bytecode modification (i.e. blindly stabbing the game's code while praying some other mod doesn't do the same thing in the same place). As a concrete example, there's an event for when living entities tick, we can simply register such an event, check if the entity within that event's context is for example a Creeper, and then do an AoE check for nearby players, dealing instant damage, giving them a permanent kill aura. I don't know why you would do such a thing, but if you wanted to, that's an easy and safe way of doing it. We'll delve into Forge events more deeply later, given they are incredibly important and useful for doing things not possible with the regular registries.
* Forge provides a bunch of patches and extra utilities for the game's code. Obviously, triggering a Forge event requires Forge to place an extra line of code for wherever it should be triggered (for example, at the beginning of an entity's update function, triggering the aforementioned entity update event). Additionally, there's a bunch of useful additions, allowing easy customization of some features beyond the scope of what vanilla Minecraft intended. For example, the `Block` class has a long list of extra methods for defining things like per-metadata hardness (in vanilla, a block could only have one hardness value which is shared between metadata variants), whether crops can grow on it, what tools are effective on this block (bypassing a nasty function from vanilla made from a long list of ternaries with hardcoded type and material checks), and so on.
* Forge also provides registries for elegantly adding certain things that would otherwise be hardcoded in vanilla, like block renderers (ISimpleBlockRenderingHandler, or ISBRH, which vanilla handles instead by using integer IDs for render type and then a massive switch, on top of a massive class with a separate method for every render type, it's cursed) or entity registration (the way vanilla does it is cursed, again).
* It also includes a config system which creates those .cfg files you might be familiar with.
* Forge also has built-in model loaders allowing to load certain model formats that vanilla Minecraft wouldn't support, like Wavefront OBJ files (the stock parser is quite bad) and Techne files (Techne is what we used before the SMP Toolbox was a thing, and the SMP Toolbox is what we used before Blockbench).
* Another thing incredibly important especially for tech/tool/material mods is the ore dictionary, a way to give standardized "labels" to certain items in order to make them compatible with similar items from other mods. Before the ore dictionary, you had to use copper from mod X to make the boiler from mod X, while mods Y and Z also added copper, you simply could not use it, unless the pack maker reconfigured the recipes. It was hell.
